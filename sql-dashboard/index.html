In a core-banking debt-collection environment, the hard part of reporting isn't the chart — it's the query underneath it. This is a look at how I build deep, multi-layered SQL reports against a sprawling case-management schema, and how the same skills keep the operation running when something breaks.

01 · Overview

What this is

I work as an IT Business Specialist in a core-banking collections operation. When a loan defaults, the case moves through a long legal pipeline — pre-legal dunning, payment plans, garnishment, insolvency, litigation — handled together with external law firms.

Almost every business question lands on my desk as a SQL problem: which closed cases are worth reactivating, how a single case really looks across fifteen sub-systems, where the fees went, or — when a batch process breaks — which records are now in an inconsistent state. The reports feed business decisions directly; there's no BI tool doing the thinking, the thinking is in the query.

02 · The challenge

Why one column is hard

The data model is large and deeply normalised. A seemingly trivial value hides real complexity. Take "the debtor's last payment": payments live in a bookings table, each tagged with a booking key, and only a specific set of keys count as an actual incoming payment — others are fees, reversals or internal postings. So "last payment" means: filter to the right booking keys, take the most recent by value date, per case.

Now multiply that by twenty columns — active workflow, current decision step, latest history entry, total claim, payment progress, enforcement title, insolvency status, last document — each with its own "latest record per case" logic. That's the real job.

  • Dozens of tables, one row per case in the output
  • "Latest / most relevant record" needed per sub-entity
  • Domain rules baked into the SQL (which keys, which statuses count)
03 · Approach

How I build it

The backbone is OUTER APPLY with SELECT TOP 1 … ORDER BY — one isolated sub-query per fact, each pulling exactly the latest relevant record for that case without fanning out the result set. Where I need ranking across a whole set I switch to ROW_NUMBER() OVER (PARTITION BY … ORDER BY …) inside a CTE and keep rn = 1.

Domain logic sits in CASE WHEN expressions and curated IN (…) lists of booking keys. Parameters go in a small WITH parameters AS (…) block and are CROSS JOINed in, so the same report can be re-run for different date ranges or owners without touching the body.

05

When it breaks: incident analysis

Reporting and incident response are the same skill under pressure. A real pattern: a nightly batch leaves cases in a broken state, the team is blocked, and someone has to find exactly which records are affected — fast.

Critical incident — operations blocked

Orphaned cases after a failed batch run

A batch job stopped halfway. The result: a set of cases left with no active workflow and no open task — invisible in the front-end work queues, so they'd silently stop being worked. No error, no alert; just cases quietly falling out of the process.

My job wasn't to fix the batch — it was to tell the team exactly which cases were affected, with their remaining claim and last known procedural state, so they could be re-queued and the damage quantified. The query uses NOT EXISTS on both workflows and tasks, plus OUTER APPLY for the latest claim and procedure status.

07 · Impact

What it delivered

  • Reports that let the business decide which closed cases to reactivate — turning dormant files back into recovered cash
  • 360° case profiles that replaced hours of manual cross-referencing across sub-systems with a single query
  • Fee breakdowns precise enough to audit cost recovery per case
  • Fast, accurate incident analysis that let the team recover from batch failures with quantified exposure instead of guesswork
