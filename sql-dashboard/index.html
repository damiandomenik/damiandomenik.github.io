01 · Overview

What this is

When a loan defaults, the case runs through a long legal process: pre-legal dunning, payment plans, garnishment, insolvency, litigation, worked together with external law firms. That process raises a steady stream of questions that can only be answered with data, and writing the SQL to answer them is a big part of my day-to-day.

This case study is about that work specifically. It doesn't try to cover everything I do. It stays on the SQL: the kind of reports and analyses I build and the thinking behind them. 02 · The challenge

Why one column is hard

The data model is large and deeply normalised, so a value that sounds trivial usually isn't. Take something like "the debtor's last payment". Payments sit in a bookings table where every row has a booking key, and only a specific set of those keys is an actual incoming payment. The rest are fees, reversals or internal postings. So even that one value means: filter to the right keys first, then pick the row that counts for that case.

Different reports need different things from the same tables. Sometimes the most recent record, sometimes a sum across a group of keys, sometimes just whether something exists at all. Put twenty of those columns next to each other (active workflow, current decision, history, total claim, payment progress, enforcement title, insolvency status) and each one has its own rule for what counts. Get one rule slightly wrong and the number looks right but isn't, and usually nobody notices. So the real work is knowing the data and the rules behind it, not just writing SQL.

  • Dozens of tables, but the output is one clean row per case
  • Each column needs the right record: latest, summed, or just present
  • The business rules live in the SQL: which keys, which statuses, which dates count
03 · Approach

How I build it

Most of it comes down to picking the right tool per column. When I need one specific record for a case, I use OUTER APPLY with a small focused sub-query. Each one has its own WHERE clause to drop everything that doesn't qualify, and when I want the most recent record, an ORDER BY … DESC with TOP 1 so I actually keep the current one and not whatever the engine returns first. That filter-then-order step is where the correctness comes from. Other columns aren't "latest" at all. They're a SUM over a group of booking keys, or just a check whether something is there.

When I need to rank across a whole set instead of one fact at a time, I use ROW_NUMBER() OVER (PARTITION BY … ORDER BY …) in a CTE and keep rn = 1. Domain logic goes into CASE WHEN expressions and curated IN (…) key lists. Parameters sit in a small WITH parameters AS (…) block that I CROSS JOIN in, so the same report runs for a different date range or owner without changing the body.

What I enjoy about this work is the mix of technical and business logic. Writing the query is rarely the hard part. The real challenge is figuring out which data actually counts under the business rules, and how all the pieces fit together.

That's the part I find genuinely interesting. The value isn't just in knowing SQL; it's in understanding both the data and the process behind it. When you know how the system works and what the business is really asking, you can turn a vague question into a clear and reliable answer, which saves a lot of time and guesswork.

05

When it breaks: incident analysis

Reporting and cleanup are the same skill pointed at different problems. Records end up in a bad state for all sorts of reasons: a batch that stopped halfway, an application bug, a workflow set up wrong, or someone clicking the wrong thing. Whatever the cause, the fix usually starts the same way. You write a query that finds exactly which records are affected, so the cleanup is done on facts instead of guesses.

Critical incident — operations blocked

Orphaned cases with no workflow and no task

One case that comes up again: cases that end up with no active workflow and no open task. They drop out of the front-end work queues, so they quietly stop being worked. No error, no alert, just cases falling out of the process. The cause might be a half-finished batch run or a workflow that didn't close properly. Either way the record is still in the database, it's just not visible in the front end.

Challenge

Cases dropped out of the work queues. No longer worked, no warning, and still real money outstanding on them.

Investigation

Found the cases that had fallen out of the process completely, and pulled each one's remaining claim and last known procedural state next to it.

Result

The full affected set found in well under an hour, each row with its outstanding amount and where it had stalled.

Impact

Cases put back into the queue before they slipped through, and the exposure quantified instead of guessed.

06

Fixing what the UI can't

Finding the bad records is one half. The other half is fixing them, and not everything can be fixed from the front end. Sometimes the screen doesn't show the field, sometimes it doesn't hold the raw value the database does, and sometimes there's just no button for the situation you're in. In those cases the fix is a carefully scoped SQL UPDATE.

Saves manual effort

Work that would take the team hours or days of clicking through cases one by one can often be done in seconds with one well-scoped update, applied to every affected case at once.

Always tested first

Updates never run blind on production. They're tested on a test environment together with the business first. Only after the test is confirmed and signed off do I get the go-ahead to run it on prod.

Time-critical

When a critical issue blocks cases in their workflows, speed matters. While they're stuck they aren't pushed forward, and their legal deadlines aren't either. Fixing it fast keeps the cases and the dates on track.

The two 🔧 Data fix tabs in the explorer above show how this works. Always a SELECT first, to confirm exactly which rows are affected, then the matching UPDATE with the same filter. The sign-off (test result, business confirmation, release to prod) normally lives in the ticket system, Azure DevOps or Jira, so there's a clear trail behind every change.
